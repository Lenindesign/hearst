## Current token inventory

The current checkout contains:

- 435 core tokens in `tokens/core/global.json`;
- 29 publication-theme JSON files in `tokens/brands/`;
- 13 semantic token files under `tokens/semantic/`;
- typography overrides in `tokens/brands/_meta.json`;
- generated `[data-brand]` CSS for the registered publication themes.

Counts are diagnostic evidence, not a compatibility contract. Additions, renames, and removals still follow the public-change and deprecation rules in **Delivery / Governance**.

## Change workflow

### 1. Establish the production need

Name the affected production component, route, state, and publication themes. If the token only supports an unverified concept, keep the work outside indexed Storybook until the component has production authority.

### 2. Reuse before adding

Search canonical core, semantic, and component tokens. Prefer an existing semantic role over a new value-specific name. A new component token should describe purpose, variant, and state rather than a particular screen.

Component-token promotion is a cross-brand decision, not a same-value search.
Run `npm run tokens:validate` and review every publication mode before replacing
a component role with a broader semantic role.

| Current validator result | Evidence | Decision |
|---|---|---|
| `component.hr.border.default` → `palette.neutral.400` | Equivalent in all 29 publication modes | Eligible for consumer migration |
| `component.rating.star.empty` → `palette.neutral.600` | Equivalent in all 29 publication modes | Eligible for consumer migration |
| Inline-link default and hover | Diverge in 16 and 9 publication modes | Keep the component roles |
| Brand divider | Car and Driver intentionally differs from `palette.brand.1` | Keep the component role |
| Full rating star | Delish intentionally differs from the shared highlight color | Keep the component role |

“Eligible” does not mean “delete immediately.” Confirm actual consumers,
migration impact, and deprecation requirements first. The validator reports the
specific modes that block an alias so a matching base value cannot be mistaken
for a safe system-wide replacement.

### 3. Edit canonical JSON

Change the smallest file that owns the decision:

| Scope | Canonical location |
|---|---|
| Shared primitive value | `tokens/core/global.json` |
| Semantic alias or role | `tokens/semantic/` |
| Publication override | `tokens/brands/{slug}.json` |
| Publication typography metadata | `tokens/brands/_meta.json` |

Do not hand-edit `src/lib/tokens.css` or `src/lib/brands.ts`.

### 4. Generate and validate production output

```bash
npm run build-tokens
npm run quality
npm run build
```

Review the generated diff. A successful command does not replace visual review of the affected production component, states, and publication themes.

### 5. Update the Storybook specification

- Render the production component that consumes the token.
- Cover the affected states and required widths.
- Compare with the routed application at the same theme, state, and viewport.
- Update a stable visual baseline only after confirming the change matches production intent.
- Record exceptions and missing evidence.

### 6. Review and merge

The pull request lists canonical token names, consumer components, themes, screenshots, automated results, accessibility checks, and compatibility impact. Accountable roles are defined in **Delivery / Governance**; the current repository does not yet enforce those roles through `CODEOWNERS`.

### 7. Deliver to external design tools when required

Generate a payload only after the Git change is approved:

```bash
npm run push-figma > figma-payload.json
npm run push-pencil > pencil-payload.json
```

The command names are historical. Both scripts currently generate JSON only. An authorized destination write is a separate action.

### 8. Verify each destination

For Figma or Pencil, record:

- destination file and revision;
- canonical names present;
- expected publication modes or themes;
- resolved values compared with Git;
- failures, skipped tokens, and unsupported types;
- the person or automation that performed the authorized write.

Never put credentials or private file identifiers in Storybook, generated screenshots, or pull-request descriptions.

## Status vocabulary

Use evidence-based status rather than a tool-specific Jira lifecycle:

| Status | Meaning | Required evidence |
|---|---|---|
| **Proposed** | Need and ownership are still being reviewed | Production consumer and intended semantic role |
| **In review** | Canonical change and specification are in a pull request | Token diff, Storybook evidence, quality results |
| **Merged** | Canonical change is in the target branch | Exact source revision |
| **Generated** | Application or external-tool payload was created | Command output and generated diff or payload summary |
| **Verified in destination** | Authorized external write was checked | Destination revision, names, themes/modes, and values |
| **Released** | A published production artifact was verified | Deployment or package revision and smoke-test evidence |

`Generated`, `merged`, and `released` are different states. Do not describe a payload as synchronized, a merge as deployed, or a green Storybook build as production-ready without the corresponding evidence.

## Known pipeline gaps

- External Figma and Pencil writes do not produce a repository-owned sync receipt.
- `build-from-tokens.ts` and the Figma/Pencil payload generators do not directly read all 13 files under `tokens/semantic/`; the relationship between those canonical files and shipped or delivered output requires an explicit coverage test.
- The repository contains legacy bidirectional and Token Studio scripts. They must not be used to override canonical Git tokens without an explicit migration decision.
- Deployment configuration exists, but a provider result and exact deployed revision must be checked before calling a token live.
- No formal versioned package release currently measures the deprecation window.
