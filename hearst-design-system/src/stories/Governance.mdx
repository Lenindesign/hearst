> **Current enforcement gap:** these are accountable review roles, not resolved GitHub identities. The repository has no `CODEOWNERS` file. Administrators must map the roles to real teams or users before required review can be enforced automatically.

## Change classification

| Change | Use when | Required evidence |
|---|---|---|
| **Patch** | Compatible bug fix, documentation correction, or token correction | Updated Storybook specification and focused regression evidence |
| **Minor** | Backward-compatible component, prop, token, or variant | New states and API guidance, responsive and accessibility evidence, changelog entry |
| **Major** | Removed or renamed export, prop, behavior, story ID, or canonical token | Migration example, deprecation history, announced removal, major release |

## Deprecation contract

A public component, prop, story ID, or canonical token is not removed in the same release that deprecates it.

1. Mark the API deprecated in its TypeScript documentation and Storybook page.
2. Name the replacement and provide a copyable migration example.
3. Record the change in `CHANGELOG.md`.
4. Preserve compatibility for at least one minor release and 30 days, except for security or data-integrity emergencies.
5. Announce the removal release in advance and remove the compatibility path only in a major release.

## Contribution evidence

Every shared change should identify:

- the issue and reader or consumer impact;
- affected components, tokens, routes, and publication themes;
- the production source and the Storybook specification that represents it;
- numbered screenshots or Storybook links for the changed states;
- keyboard, screen-reader, zoom, touch-target, and viewport checks performed;
- automated quality and application-build results;
- migration and rollback notes when the public API changes.

The complete state and responsive acceptance criteria live in `CONTRIBUTING.md`. Exploratory or unverified work belongs in `src/storybook-candidates`, which Storybook intentionally does not index.

## Release checklist

1. Move the relevant `Unreleased` entries into a dated version heading.
2. Confirm patch, minor, or major impact from public API and canonical-token changes.
3. Run `npm run quality` and `npm run build`.
4. Attach Storybook, responsive, accessibility, and visual evidence to the release review.
5. Obtain the accountable reviews defined above.
6. Verify the published artifact and its exact source revision before declaring the release complete.
7. Run `STORYBOOK_URL=https://hearst-design-system.netlify.app/storybook/ EXPECTED_REVISION=<full-commit-sha> npm run verify:storybook:deployment` and confirm that the published revision and catalog counts match the reviewed artifact.
