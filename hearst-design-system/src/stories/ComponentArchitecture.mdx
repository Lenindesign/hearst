# Hearst+ component architecture

## HDS ownership, shadcn conventions, Base UI behavior, and Tailwind styling

Hearst+ does not ship a generic component library unchanged. Its reusable controls are **Hearst-owned React components** that combine HDS semantic tokens, Tailwind CSS utilities, shadcn/ui composition conventions, and Base UI interaction primitives.

## Are the HDS primitives shadcn components?

**They are Hearst-owned components built with shadcn/ui conventions.** The source is checked into this repository under `src/components/ui/`, where it is adapted to HDS tokens and Hearst+ requirements. Updating shadcn does not automatically replace the product components.

For controls such as Button, Switch, and Tabs:

1. Base UI provides the accessible headless primitive.
2. The local component defines its public React API and variants.
3. Tailwind classes compose layout, interaction states, and responsive behavior.
4. HDS semantic CSS variables supply the active Hearst+ or publication theme.

```tsx
<Button
  variant="outline"
  className="border-border bg-background text-foreground hover:bg-muted"
>
  Save story
</Button>
```

The class names express the component treatment, while `border`, `background`, `foreground`, and `muted` resolve through the active HDS theme rather than fixed brand colors.

## Primitive and product boundaries

| Layer | Examples | Reuse expectation |
|---|---|---|
| HDS primitive | Button, Input, Switch, Tabs, Badge, Avatar, Divider | Reuse before creating another control with the same responsibility |
| Editorial component | ArticleCard, ArticleByline, ArticleHero, Grid, media treatments | Reuse across feed and reader contexts when the content contract matches |
| Hearst+ product module | Story river, Daily Habit, Trending, Delish Shorts, personalization console | Product-specific composition built from primitives, tokens, and editorial components |
| Page template | HomePageTemplate and article-reader templates | Integrated product behavior, providers, routing, and responsive composition |

Not every visual element must be a Base UI primitive. Static editorial composition can use semantic React markup and Tailwind directly. Interactive controls should reuse the local HDS primitive when one already owns the required behavior.

## Token flow

```text
HDS token JSON
  -> Style Dictionary output
  -> generated CSS variables
  -> Hearst+ and publication theme aliases
  -> Tailwind semantic utilities or arbitrary variable utilities
  -> local component and product-module styles
```

Use semantic classes such as `bg-background`, `text-foreground`, and `border-border` for shared UI meaning. Use scoped Hearst+ variables such as `var(--hp-surface)` only when the product contract is specifically owned by Hearst+. Do not hard-code a publication color into a reusable primitive.

## Developer decision guide

1. **Start with an existing HDS primitive.** Check `src/components/ui/` before adding a new control.
2. **Use Base UI for complex interaction.** Prefer a headless primitive for focus, keyboard, selection, disclosure, or modal behavior.
3. **Style with Tailwind.** Keep responsive and state styling close to the component.
4. **Resolve appearance through HDS tokens.** Shared components must inherit destination and publication themes.
5. **Compose product behavior above the primitive layer.** Ranking, feeds, readers, and video behavior do not belong inside Button, Badge, or Tabs.
6. **Document and verify states in Storybook.** Cover default, hover, focus, disabled, selected, dark mode, and relevant responsive ranges.

## Accuracy rule

Describe the stack as:

> **Hearst-owned components built with shadcn/ui conventions, Base UI accessibility, Tailwind CSS 4, and HDS semantic tokens.**

Do not describe the primitives as generic shadcn components, and do not imply that Tailwind or Base UI owns the Hearst visual system.
