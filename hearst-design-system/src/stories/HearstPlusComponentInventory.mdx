**Registry limit:** rendering in Storybook does not make a component production-owned. A production claim requires the shipped React source plus an application import site; the story supplies an executable specification of that same boundary. The generated registry inventories code, metadata, direct application import sites, direct story mappings, and validated explicit integrated or infrastructure classifications; `/index.json` inventories the running catalog. The ownership-classification queue still requires human review of whether a module is a reusable component, an integrated boundary, a route/template, or internal support code.

## Design-system tooling boundary

The routed design-system documentation site is also production software, but its shell is not a Hearst+ reader component. `NavBar` is therefore specified under **Design System Tooling / Navigation**, outside the Hearst+ hierarchy. Four direct stories use the exact `DesignSystemNavBar` renderer to cover the documentation-home state, component subnavigation, the mobile-open disclosure, and keyboard dismissal with focus restoration. The live wrapper supplies only the current Next.js pathname and environment-aware Storybook URL.

This separation prevents the internal tool header from being offered as product navigation. The tooling specification still enforces one page-level heading, named navigation regions, a named brand-preview selector, current-page semantics, 44px phone controls, Escape dismissal, no horizontal clipping at the reviewed desktop width, and automated color contrast.

`ProductStoryShell` is the second explicit tooling boundary. It supplies the shared stakeholder modules used by the routed Product Story, Why Hearst+, Product Blueprint, and Token Architecture pages; it is not a reader-facing Hearst+ shell. Nine stories under **Design System Tooling / Product Specification Modules** import the exact production exports for the shared header, illustrative navigation and story concepts, current portfolio facts, journey/ranking diagrams, architecture/palette references, publication style guide, and portfolio marquee. Static diagrams are identified as figures rather than interactive product controls, illustrative cards say so in their accessible names, and the shared navigation preserves one visible current-page state, 44px targets, and page-level overflow containment from 320px through desktop.

## Keep these integrated

- **Theme runtime:** the global toolbar adapter now implements the complete production `ThemeContext` contract, while **Foundation / Theme Runtime** mounts the exact production `ThemeProvider` to verify publication switching, generated variables, Hearst Flux dark default, mode toggling, document synchronization, and disabled persistence. Keep adapter behavior and exact-provider evidence distinct; a toolbar preview alone is not proof of the production runtime.
- **Reader account provider:** `ReaderAccountProvider` is explicitly classified as non-visual application infrastructure. The root application layout and the global Storybook decorator mount the same provider; account presentation remains in the production `ReaderAccountUI` stories, while pure normalization and merge behavior stay in `reader-account-model` tests. Its metadata records the real prototype boundary: browser-local credential state, sync-id profile access without a production server session, no production consent or retention contract, and local-only deletion. A standalone provider card would invent UI and duplicate the real account surfaces.
- **Product specification shell:** keep the exact stakeholder modules under **Design System Tooling**, not under reader Components or Templates. - **Legacy FRE article primitives:** `ArticleHero`, `ArticleByline`, `ArticleBody`, `RelatedArticles`, and `AdPlaceholder` are exported through the FRE barrel but currently terminate in the unrouted `ArticlePageTemplate` or design-system layout examples. The shipped `/read/[storyId]/` experience uses the separate Hearst+ reader boundaries. Keep these modules in the ownership-classification queue until a routed production consumer exists; do not promote the quarantined Article Page story as evidence.

- **Reader modal and river orchestration:** the dialog shell, responsive masthead, queue selection, navigation/return contract, source readiness, comments, contextual recommendations, desktop context rail, desktop reader advertisement, inline river advertisement, Brand Spotlight rendering and selection, action bar, article-body rendering, fullscreen image viewer, and Ambient Reader are extracted production boundaries. ## Verified quality gate

Run these checks before publishing Storybook or changing a shared component:

```bash
npx tsc --noEmit
npm run test:unit
npm run test-storybook
npm run test:storybook:responsive
npm run build-storybook
npm run build
```

The browser suite covers every indexed story and reports the exact current count during each run. The responsive suite covers all indexed stories at the four required widths and writes `reports/storybook-responsive.json`. Automated accessibility violations in rendered stories fail the browser suite, but the result does not replace manual assistive-technology, zoom, or touch testing. The production build remains a separate gate because Storybook deliberately uses compact static fixtures and blocks same-origin Next.js API calls instead of pretending its catalog is a live application server.

## Definition of done for a shared story

1. Imports the production component; it does not recreate the markup.
2. Uses current checked-in Hearst metadata from the generated fixture, or clearly labels an explicit interaction-state fixture.
3. Exposes meaningful behavior such as save, open, hide, carousel, or navigation state.
4. Works with the brand toolbar through semantic HDS tokens.
5. Covers keyboard focus and a 320px or 390px viewport when interaction is responsive.
6. Documents scoped exceptions instead of turning them into global variants.
