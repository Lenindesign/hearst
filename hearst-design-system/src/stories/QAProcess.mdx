## Pull-request checkpoint

Before merge, the changed production component, token, or route and its Storybook specification must agree.

### Required automated evidence

Run:

```bash
npm run quality
npm run build
```

`npm run quality` currently covers:

- canonical-token structure, validation, and no-regression hard-coded-style auditing;
- publication metadata validation;
- unit tests for shared models;
- all indexed Storybook interaction and automated accessibility scenarios;
- the Featured Carousel keyboard traversal;
- reviewed visual-regression cases;
- every indexed story at 320, 390, 768, and 1,280px for render errors and horizontal page overflow;
- every indexed documentation page at 390 and 1,280px for headings, render errors, browser errors, and horizontal page overflow.

Automated checks are a floor. They do not prove complete screen-reader usability, 200% zoom, forced-colors behavior, touch behavior, or correctness against an external production deployment.

### Required review evidence

- Name the production component, route, or canonical token file.
- Link the corresponding Storybook story or documentation page.
- Attach numbered before/after screenshots for stable visual changes.
- List the publication themes and required states reviewed.
- Record keyboard, screen-reader, zoom, reduced-motion, and touch checks applicable to the change.
- Classify public API changes as patch, minor, or major.
- Include migration and rollback guidance when compatibility changes.
- Record any unavailable evidence as an explicit limitation.

## Production-parity review

Storybook is a specification of production-owned interfaces, not an independent design proposal.

| Review | Pass criteria |
|---|---|
| **Component source** | The story imports the same production component or composition used by the routed application. |
| **Behavior** | Production owns state transitions, focus, keyboard behavior, and responsive logic; the story does not recreate them. |
| **Content fixture** | Checked-in fixture content is current, deterministic, and representative; any synthetic interaction state is labeled. |
| **Themes** | Destination foundation tokens load before publication overrides, matching the routed application. |
| **Responsive** | Required widths render without page overflow; component-specific reflow and touch behavior are reviewed. |
| **Accessibility** | Automated findings fail the test suite, and changed journeys receive manual keyboard and assistive-technology review. |
| **External production** | When an external deployed app is part of the release, compare the exact route, state, viewport, and source revision before claiming parity. |

Unverified work belongs in `src/storybook-candidates`, which Storybook intentionally does not index.

## Token-change checkpoint

Canonical token JSON under `tokens/` is the editing surface. Generated CSS, TypeScript, Figma payloads, and Pencil payloads are delivery outputs.

1. Update the smallest canonical token that owns the design decision.
2. Run `npm run build-tokens`.
3. Run `npm run quality` and `npm run build`.
4. Review affected production components in Storybook across the relevant publication themes.
5. Generate external-tool payloads only after the Git change is approved.
6. Verify the actual external write in the destination tool; payload generation alone is not synchronization.

## Visual-regression checkpoint

Stable production-backed states have reviewed PNG baselines.

- Run `npm run test:visual` to compare current output with reviewed baselines.
- Use `npm run test:visual:update` only after comparing the changed component with the production authority.
- Never refresh a baseline solely to make the gate pass.
- Keep interaction stories separate from stable visual stories when an interaction changes state while capture is in progress.
- A green baseline proves stability against that reviewed image, not correctness for every publication or content combination.

## Release checkpoint

The project does not currently define a formal versioned package release. Until one is established, changes remain under **Unreleased** in `CHANGELOG.md`.

Before describing a change as released:

1. Complete the repository quality workflow and application build.
2. Obtain the accountable reviews defined in **Delivery / Governance**.
3. Record consumer impact and compatibility in `CHANGELOG.md`.
4. Publish through the authorized release or deployment process.
5. Verify the resulting artifact, route, and exact source revision.
6. Record deployment-specific smoke tests and remaining limitations.

A local build, a passing Storybook suite, a merge to `main`, or a generated Figma/Pencil payload is not by itself proof of a production release.

### Published Storybook verification

The static Storybook artifact includes `build-info.json` with its exact source
revision, build context, build time, and catalog counts. After the authorized
deployment is complete, run:

```bash
STORYBOOK_URL=https://hearst-design-system.netlify.app/storybook/ EXPECTED_REVISION=<full-commit-sha> npm run verify:storybook:deployment
```

The command fails when the provenance file is missing, the deployed revision is
not the reviewed revision, the built and published catalog counts disagree, or
the endpoint does not respond within the bounded verification timeout.

## Current gaps

| Gap | Impact | Recommended evidence |
|---|---|---|
| No `CODEOWNERS` mapping | Documented review roles are not automatically requested or enforced | Add real team/user mappings after repository administrators confirm ownership |
| No repository evidence for Jira automation | Status transitions and ticket gates cannot be treated as system behavior | Link the authoritative Jira workflow or configure and test the integration |
| No repository-owned Storybook preview workflow | Pull-request preview availability cannot be promised | Add and verify a preview workflow, then document its URL and revision contract |
| External token writes are manual | Payload generation can be mistaken for successful synchronization | Add destination verification output and retain a non-secret sync record |
| No formal versioned package release | Deprecation timing and semantic versions cannot yet be measured against published versions | Establish the package artifact, registry, version source, and release workflow |
| Manual accessibility evidence is not stored consistently | Automated success may be mistaken for conformance | Add a compact review template for screen reader, zoom, forced colors, reduced motion, and touch |
