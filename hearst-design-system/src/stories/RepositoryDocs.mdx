# Repository docs

The Markdown files in this repository are the working memory for the Hearst+ prototype. They help stakeholders understand what the product is, what is already implemented, where decisions live, and which source to use before requesting a change.

<HearstPlusDocScope owner="Cross-functional" source="PRODUCT.md; DESIGN.md; DESIGN-SYSTEM-SPEC.md; STYLE.md; BRAND_STYLES.md; APP_RULES.md; VAULT_HOME.md; DECISION_LOG.md; CONTRIBUTING.md; notes/README.md">
  Use this page as the plain-language map for repository documentation. The Markdown files guide decisions, but the routed Next.js prototype, production React components, canonical token files, and Storybook stories remain the evidence that a rule is applied.
</HearstPlusDocScope>

## The simple rule

Start with `PRODUCT.md`. Then open only the file that owns the question in front of you.

Do not read every document for every change. The docs are organized by ownership so product, design, engineering, and leadership can move quickly without duplicating rules or carrying stale context.

## Reference files

| File | What it is for | How to use it |
|---|---|---|
| `VAULT_HOME.md` | Complete knowledge map | Open it when you need the broad repo map or cannot find the right owner. |
| `CONTRIBUTING.md` | Practical contribution workflow | Use it for local setup, verification expectations, and how to avoid stale documentation. |
| `DECISION_LOG.md` | Historical rationale | Use it only after checking the current canonical rule. History explains why, but it does not override current behavior. |
| `notes/README.md` | Notes and archive policy | Use it to understand which audits, plans, and QA notes are historical context. |
| `CHANGELOG.md` | Release notes | Use it to summarize shipped changes, not to define future product behavior. |
| `README.md` | Repository entry point | Use it for setup and orientation. It should point people to the deeper owners, not repeat them. |

## Decision path

| Stakeholder question | Read first | Then verify in |
|---|---|---|
| What is Hearst+ trying to become? | `PRODUCT.md` | `/hearst-plus/` and `Hearst Plus / Product / For You Feed` |
| Why did this story appear for a reader? | `APP_RULES.md` | For You river cards, reader recommendations, and account personalization |
| Is this layout or interaction correct? | `STYLE.md` | The routed page and the matching Storybook story at desktop and mobile widths |
| Is this brand treatment correct? | `BRAND_STYLES.md` | The destination, publication route, and reader opened from that route |
| Is this token or component contract correct? | `DESIGN-SYSTEM-SPEC.md` | Token files, generated outputs, and production-backed Storybook stories |
| Where did this decision come from? | Current canonical owner | `DECISION_LOG.md` only for background |

## Maintenance rule

When a rule changes, update the canonical owner first. Then update any Storybook doc, blueprint page, README, or archive note only if it helps people find or understand the rule.

Archived audits and plans are context, not marching orders. Treat them as old snapshots until current code, Storybook, or a canonical document confirms the rule still applies.
