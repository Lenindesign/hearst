## Choose the owning surface

| Need | Start here | Do not start by |
|---|---|---|
| Change reader behavior or state | Production component or route | Editing a Storybook-only replica |
| Add or revise a shared component API | Lowest reusable production component | Adding page-specific props to a primitive |
| Change a shared visual role | Existing semantic or component token | Hard-coding a new value in JSX or CSS |
| Change one publication theme | `tokens/brands/{slug}.json` and `_meta.json` | Overriding global CSS for every brand |
| Document a supported state | Story importing the production component | Publishing an unverified concept |
| Explore an unapproved concept | `src/storybook-candidates` or an explicitly scoped design artifact | Adding it to the indexed component catalog |
| Deliver tokens to Figma or Pencil | Approved canonical token change, then payload generation | Editing the destination and assuming production changed |

## Designer workflow

### Review an existing component

1. Open the relevant Storybook story.
2. Confirm the production component and source named by the story.
3. Review default and applicable loading, empty, error, disabled, selected,
   destructive, permission, and recovery states.
4. Switch destination or publication theme only where the production component
   supports it.
5. Check 320px, 390px, tablet, and desktop behavior as applicable.
6. Record visual, interaction, accessibility, content, or specification drift
   against the routed application.

### Request a component or token change

Provide:

- the production route, component, state, and publication themes;
- user or consumer impact;
- same-state screenshots at the relevant viewport;
- the existing token or API searched before proposing a new one;
- accessibility and responsive requirements;
- acceptance criteria and any external design reference.

The team's issue tracker can carry the request, but this repository does not
prove a particular Jira workflow or automatic status transition.

### Make a canonical token edit

Designers with repository access may edit token JSON on a review branch using
their normal approved Git workflow. An AI-enabled IDE may assist, but it does
not automatically have authority to create branches, commit, open pull
requests, merge, publish, or write to external design tools.

Run the same checks required for developer changes:

```bash
npm run build-tokens
npm run quality
npm run build
```

## Developer workflow

### Set up the current checkout

```bash
npm install
npm run dev
npm run storybook
```

- Application: `http://localhost:3000`
- Storybook: `http://localhost:6006`

Use the exact ports currently configured by the scripts. Do not describe a
local server as a published production artifact.

### Change a production component

1. Read `PRODUCT.md`, `DESIGN.md`, `STYLE.md`, `BRAND_STYLES.md`,
   `APP_RULES.md`, and the relevant component specification.
2. Find the current production import and ownership boundary.
3. Change the smallest reusable component that owns the behavior.
4. Add or update the production-backed Storybook story in the same change.
5. Cover applicable interaction, responsive, accessibility, theme, and error
   states.
6. Compare Storybook with the routed application using the same state,
   viewport, theme, and content.
7. Run `npm run quality` and `npm run build`.
8. Attach the required review, migration, rollback, and release evidence.

### Change canonical tokens

```bash
npm run build-tokens
npm run quality
npm run build
```

Review the canonical and generated diffs. Never hand-edit
`src/lib/tokens.css` or `src/lib/brands.ts`.

### Deliver tokens to external design tools

```bash
npm run push-figma > figma-payload.json
npm run push-pencil > pencil-payload.json
```

These commands only generate JSON. An authorized destination write and
post-write verification are separate actions. Do not put credentials or private
file identifiers in documentation, screenshots, logs, or pull requests.

## Review evidence

Every shared change should include:

- issue and user or consumer impact;
- affected production components, routes, tokens, and publication themes;
- Storybook links or numbered screenshots;
- tested states and viewports;
- keyboard, screen-reader, zoom, reduced-motion, forced-colors, and touch checks
  applicable to the change;
- automated command results;
- public API classification;
- migration and rollback guidance;
- external-tool or deployment evidence when those systems are in scope;
- explicit limitations for evidence that was not available.

## Evidence-based status

Use:

| Status | Meaning |
|---|---|
| **Proposed** | Need and owner are being reviewed |
| **In review** | Canonical change and specification are in review |
| **Merged** | Source change is in the target branch |
| **Generated** | Application output or an external-tool payload was created |
| **Verified in destination** | An authorized external write was checked |
| **Released** | Published artifact and exact source revision were verified |

Do not collapse these states. A merge is not deployment, payload generation is
not synchronization, and a green Storybook build is not a production release.

## Current limitations

- No `CODEOWNERS` file maps documented roles to enforced reviewer identities.
- No repository evidence proves Jira automation.
- No repository-owned pull-request Storybook preview workflow is present.
- No formal versioned package release is established.
- No sync receipt or round-trip test covers external design tools.
- Legacy Pencil and Token Studio paths retain conflicting authority.
- Manual accessibility evidence is not stored consistently.
